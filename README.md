 2. Database and Table Design
 Table        Purpose                              Primary key                 Foreign key
 `suppliers`  Companies that supply medicines    `supplier_id` (identity)     none (parent) 
 `medicines`  Medicines in stock              `medicine_id` (identity)        `supplier_id` -> `suppliers` 
 `sales`  Sales of medicines to customers   `sale_id` (identity)         `medicine_id` -> `medicines` 

Relationships: one supplier supplies many medicines (`1 to 0..*`); one medicine appears in many sales (`1 to 0..*`). Primary keys uniquely identify each row and are generated by the database (`GENERATED ALWAYS AS IDENTITY`). Foreign keys guarantee every medicine has a real supplier and every sale a real medicine, which avoids duplicated supplier/medicine data and keeps records consistent.

### Task explanations
- **Q1.1-Q1.3 SELECT:** list names/prices, filter low stock (< 50), and sort by price descending.
- **Q2.1 INNER JOIN:** returns only medicines that have a matching supplier. **Q2.2 LEFT JOIN:** returns every medicine; `NULL` sale columns mean the medicine was never sold. **Q2.3:** joins sales, medicines and suppliers into one sales report with a computed total.
- **Q3.1-Q3.3 UPDATE:** one record by name, a group by supplier, and a rule-based 10% discount on near-expiry stock. Each was previewed with a SELECT using the same WHERE and verified afterwards.
- **Q4.1-Q4.3 ALTER TABLE:** renamed `sales.customer_name` to `buyer_name`, widened `suppliers.phone` to `VARCHAR(20)`, and added `medicines.manufacturer`. Structure verified through `information_schema.columns`; existing data stayed intact.
- **Q5.1-Q5.3 INSERT:** one medicine, two suppliers in a single statement, and a sale linked to an existing medicine through a valid foreign key.
